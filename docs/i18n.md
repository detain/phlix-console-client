# Internationalization (i18n) Guide

This document describes the i18n system for the Phlix console client and explains how to convert remaining screens.

## Overview

The console client uses SugarCraft's `SugarCraft\Core\I18n\T` translation system, wrapped by `Phlix\Console\I18n\Lang`. All user-facing strings should be routed through `Lang::t()` or `Lang::_()` so they can be translated to other languages.

## Translation Catalog

- **Location**: `resources/lang/`
- **Format**: PHP files returning a `array<string, string>` keyed by dot-separated names (e.g., `'recommendations.title'`)
- **Default locale**: `en.php` (English) — the source of truth for key sets
- **Shipped locales**: `en`, `es`, `fr`, `de`, `it`, `pt-br` (Brazilian Portuguese), `ja`

## How to Use

### Basic translation

```php
use Phlix\Console\I18n\Lang;

// Simple key lookup
Lang::t('recommendations.title');  // => "For You"

// With interpolation (uses {name} placeholders)
Lang::t('detail.more_cast', ['count' => 5]);  // => "  +5 more"

// Shorthand alias
Lang::_('recommendations.hint');  // => "Q: Back  ↑↓: Navigate  Enter: Open  X: Dismiss"
```

### Placeholder syntax

Translation values use `{name}` placeholders:

```php
// In resources/lang/en.php:
'detail.more_cast' => '  +{count} more',

// In code:
Lang::t('detail.more_cast', ['count' => $remaining]);
```

### Locale detection & resolution

At app boot, `App::boot()` runs `T::setLocale(Locale::current())`. The chain
`LC_ALL → LC_MESSAGES → LANG` is read, and each raw value is resolved onto a
shipped catalog by `Phlix\Console\I18n\Locale`:

| Environment value (examples) | Catalog |
|------------------------------|---------|
| `es`, `es_ES.UTF-8`, `es-MX`, `Es-es` | `es` |
| `fr`, `fr_FR.ISO-8859-1`, `fr-CA` | `fr` |
| `de`, `de_DE.UTF-8@euro`, `de-AT` | `de` |
| `it`, `it_IT.UTF-8` | `it` |
| `pt_BR.UTF-8`, `PT_BR.utf8`, `pt-BR`, `pt`, `pt-PT` | `pt-br` |
| `ja`, `ja_JP`, `JA_JP.UTF-8` | `ja` |
| `en`, `en_GB`, anything unsupported, `C`, `POSIX`, unset | `en` |

Normalization rules: the encoding/modifier suffix (`.UTF-8`, `@euro`) is
dropped, `_` becomes `-`, the value is lower-cased, region tags fall back to
their language, and only the seven codes in `Locale::SUPPORTED` can ever be
returned. `pt` has no bare-language catalog, so **all** Portuguese variants
deliberately land on the Brazilian one.

The file name is vendor-canonical lowercase-hyphen: the loader (and
`Locale::normalize`) maps `pt_BR` → `pt-br`, so the Brazilian catalog is
`pt-br.php` — a file literally named `pt_BR.php` would never be found.

Manual override at any point:

```php
use Phlix\Console\I18n\Locale;
use SugarCraft\Core\I18n\T;

T::setLocale(Locale::resolve('pt_BR.UTF-8')); // or any catalog code
```

### Fallback semantics (per key, not per file)

The vendor resolver (`SugarCraft\Core\I18n\T::translate`) falls back **per
key**: for locale `pt-br` it tries `pt-br.php`, then the base-language file
`pt.php`, then `en.php`, then the raw key. So a locale file that lags en.php
degrades to English for only the missing keys — never mixed broken output.
Key drift is nonetheless forbidden by CI (`composer i18n:check`,
`tests/I18n/LocaleCatalogsTest.php`): a lagging catalog is a bug to fix, not
a state to ship in.

## Converting a Screen

### Step 1: Add the import

```php
use Phlix\Console\I18n\Lang;
```

### Step 2: Identify user-facing strings

Look for:
- Hardcoded strings in `view()` methods
- Strings used in `Chrome::frame()` calls
- Error messages shown to users
- Menu options, hints, and labels

### Step 3: Add keys to the catalog

Add entries to `resources/lang/en.php`:

```php
return [
    // ... existing keys ...

    // ---- YourScreen ------------------------------------
    'yourscreen.title' => 'Your Title',
    'yourscreen.hint' => '↑↓  navigate      Enter  select      Esc  back',
    // ... etc
];
```

### Step 4: Replace hardcoded strings

Replace hardcoded strings with `Lang::t()` calls:

```php
// Before:
return Chrome::frame('Settings', $body, 'Enter  save      Esc  cancel', ...);

// After:
return Chrome::frame(Lang::t('settings.title'), $body, Lang::t('settings.hint'), ...);
```

### Step 5: For dynamic values

Use interpolation:

```php
// In catalog:
'yourscreen.count_items' => '{count} items found',

// In code:
Lang::t('yourscreen.count_items', ['count' => $itemCount]);
```

## CI Checks

Three i18n gates run in CI (`.github/workflows/ci.yml`, `i18n` job) and locally:

```bash
composer i18n:check            # both guards below
./scripts/check-i18n-hardcoded.sh   # wrapper for the php script
php scripts/check-i18n-hardcoded.php
php scripts/check-i18n-catalogs.php
```

1. **Hardcoded-string guard** (`scripts/check-i18n-hardcoded.php`): a
   token-based scan (via `token_get_all()`) of the converted files
   (`RecommendationsScreen.php`, `DetailScreen.php`, `FilterBar.php`) that
   fails when a new single-quoted literal looks like user-facing prose
   outside a `Lang::` call. Technical values, translation keys, API paths
   and identifier-ish tokens are skipped.
2. **Catalog key-drift guard** (`scripts/check-i18n-catalogs.php`): every
   locale file must have exactly the en.php key set, identical `{placeholder}`
   tokens per key, and non-empty values.
3. **Parity test suite** (`tests/I18n/LocaleCatalogsTest.php`, run by
   `composer test`): the same invariants plus English-leftover auditing
   against a documented cognate whitelist, and ja CJK-content checks.

## Adding a New Locale (e.g. Korean)

1. Copy the key skeleton from `resources/lang/en.php` — keep the exact key
   set and order, the `// ---- Section ----` banners, the file header, and
   every structural detail: `{name}` placeholder tokens, double-space
   separators in hint strings, leading spaces (`'  +{count} …'`), the
   `"\n  "` continuation in `recommendations.empty`, trailing label spaces.
2. Translate values. Legitimate keep-as-English cases (cognates like
   `asc`/`desc`) must be added to `EN_IDENTITY_WHITELIST` in
   `tests/I18n/LocaleCatalogsTest.php` — everything else must genuinely
   translate.
3. Name the file by the vendor canonical form (lowercase-hyphen): `ko.php`,
   or `zh-cn.php`-style for regional catalogs.
4. Add the code to `Locale::SUPPORTED` in `src/I18n/Locale.php`, and add it
   to `localeFiles` in `scripts/check-i18n-catalogs.php` plus `LOCALES` in
   `tests/I18n/LocaleCatalogsTest.php`.
5. Add resolution rows to `LocaleTest::resolveProvider()` (bare code, POSIX
   shape `xx_XX.UTF-8`, case variants) and run:

```bash
composer i18n:check && composer test
```

## Notes

- Technical values (sort field names like `'name'`, `'year'`; order values `'asc'`, `'desc'`) are NOT translated as they are internal API values. Only their display labels are translated.
- Missing translations fall back per key: active-locale file → base-language file → `en.php` → the raw key itself, so no string is ever lost or silently blank.
- Tests run against the English catalog by default; per-locale behavior is covered by `tests/I18n/LocaleCatalogsTest.php`.
- `detail.missing_episodes_one`/`_many` and `detail.{season,episode,item}_plural` exist because this i18n layer has no CLDR plural rules: en/it/pt-br/ja pick singular/plural keys by `count === 1` in code; languages with richer plural systems would eventually need more forms (and keys) — that is an accepted, visible TODO rather than silent mispluralization.
